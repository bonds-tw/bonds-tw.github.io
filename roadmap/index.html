擋在最前面的那件事

上一版是 TW FidO SP 資格。測試憑證到位後，路障換人了——而且換成小很多的一個。

已解鎖：TW FidO 模擬測試憑證到位

取得了走行憑正式環境的模擬測試 SP 憑證，getSpTicket / getAthOrSignResult 現在可以呼叫，M2 到 M4 的開發不再需要等行政流程。

但有個必須寫下來的但書：這組 sp_service_id 與規格書 v2.9 公開範例值 逐字元相同，是模擬測試系統的共用識別碼，不是 bonds-tw 專屬憑證。 開發測試完全夠用，但正式上線前仍須向 MOICA 申請專屬 SP。 白皮書 5.2 講的行政門檻沒有消失，只是不再擋住開工。

現在的路障：Xcode 裝不起來，因為這台跑的是 macOS 27 beta

空間已清出（79 GiB 可用），但 App Store 的 Xcode 下載是死的、不是慢的—— storedownloadd 根本沒在跑。連 brew 也失敗，它要「Command Line Tools for Xcode 27.0」； softwareupdate 則只提供 macOS 27 Beta 4。

App Store 供應的是正式版 Xcode，在 beta OS 上卡住是常態。 解法是改從 developer.apple.com 直接下載 .xip，瀏覽器可續傳，不依賴那個已經死掉的 daemon。

但這不等於停工：Command Line Tools 內含 Swift 6.2，純 Swift 邏輯可以單獨編譯驗證； CI 在 GitHub 的 macOS runner 上跑，本機沒有 Xcode 也照樣有建置與測試驗收。M0 就是這樣完成的。

已拍板的決定

先把幾個會反覆被問的問題定住，免得每次開工都重新吵一次。

D-01 主線是 bonds-tw/backupTW-iOS，不用個人 fork

mashbean/backupTW-iOS 與上游逐位元組相同（ahead 0 / behind 0）， 沒有承載任何工作，只會多一層同步負擔。開發一律在組織 repo 開 branch 走 PR。 這是公共財專案，程式碼的所有權、授權條款、Apple 團隊、Pages 都該掛在組織底下，而不是個人帳號。

D-02 三個 iOS 專案收斂成一個，其餘轉為素材

backupTW-iOS 是唯一接上真實政府服務的（MyData → 加密 PDF → 身分欄位）， 所以它是主幹。bond-tw-app（24 個 SwiftUI 畫面、設計系統）與 Bondbear-vanilla（完整的 ZK 驗證流程 UX、QR 掃描）都停在 2025 年 8 月、 且 ZK 部分是模擬的——把它們當 UX 藍本與畫面素材移植過來，不要三線並行維護。

D-03 ZK 只用 PSE 的成品，不自己造

privacy-ethereum 的那套（電路、Swift bindings、撤銷 SMT、Go 驗證器）每日都在更新， 且 openac-rsa-x509-swift 直接支援 iOS 16+ SPM 安裝。 我們的工作是「接上去」與「把線上流程改成離線」，不是重寫電路。

D-04 「本人可驗」與「資料可驗」是兩張憑證，不是一張

白皮書 5.2 明確要求把兩件事拆開。MyData 來的是欄位事實（無文件級簽章）， TW FidO／MOICA 來的是持有證明與意思表示。 資料模型上做成兩個 credential、以同一把裝置金鑰綁定， 日後 MyData 補上文件級簽章時，只需替換前者的信任根，不必動整個皮夾。

里程碑

M0 到 M5 是有相依順序的：M2 卡住時，M0、M1、M3 的驗證器骨架仍可平行做。 每項工作的狀態就是現況，沒有預先灌水。

M2

本人可驗：TW FidO 簽章與 ZK 證明

豆泥 · 已解鎖 · 相依 Xcode

接上 PSE 的 OpenAC，讓 App 能在本機產出「我持有有效自然人憑證」的零知識證明。

0%
  • 已完成 取得 TW FidO 測試憑證 走行憑正式環境的模擬測試 SP。但識別碼與規格書公開範例值相同，非專屬憑證——正式上線前仍須申請 bonds-tw 專屬 SP。
  • 進行中 以 node helper 驗證憑證可用 不需要 Xcode，今天就能做。sp_checksum 算法已對照規格書驗證：SHA-256 hex → AES-256-GCM → IV(12B)‖密文(64B)‖tag(16B)，共 184 個 hex 字元。
  • 待辦 App-to-App 簽章流程 getSpTicket → 深連結 mobilemoica://.../a2a/verifySign → 回呼 → getAthOrSignResult 輪詢。與現有 WebView 登入是兩條完全不同的路徑。
  • 待辦 整合 openac-rsa-x509-swift SPM 加依賴。sign_type 必須是 PKCS#1，電路只吃這個。
  • 待辦 選定 bonds-tw 專屬 APP_ID 31 字元 hex。nullifier 由 APP_ID ＋ 持卡人金鑰導出，不可沿用 Matters 的，否則等於共用去重命名空間。
  • 待辦 電路與金鑰下載管理 proving key 與 SMT 快照都要下載解壓（範例 App 約 10 秒）。需要斷點續傳、完整性校驗、以及「離線前先備妥」的引導。
  • 技術驗證 Spike：實機證明效能與記憶體 範例 App 數據為 prove 約 5 秒、verify 約 13 秒。必須在實機量測：Matters 實測 macOS arm64 重複產生 certChainRS4096 witness 會 SIGSEGV（upstream 假資料也會），macOS 不能當穩定性驗收環境。
M3

離線驗證：把 No Phone Home 做成真的

豆泥 · 相依 M2 · 已延後

範圍已收斂：只做「驗證離線」，不做「發證離線」。 發證階段需要 MyData 與 TW FidO，本來就得連網；要離線的是查驗現場那一端。 這是整份藍圖最需要自己動手的一段——PSE 的流程是線上的：跟伺服器要 challenge、產證明、 POST 回去驗證並在伺服器端做 nullifier 去重。白皮書 5.2 要的卻是離線點對點、不回傳、不留軌跡。 順序上排在 M2 跑通之後。

0%
  • 技術驗證 Spike：challenge 改由驗證者產生 拿掉伺服器後，防重放的 nonce 必須由驗證端當場產生並經由本地通道交付。這是能不能離線的關鍵一刀。
  • 待辦 本機驗證路徑 好消息是 OpenACSwift 已經有 linkVerify(documentsPath:)，驗證不必然要走伺服器——這就是離線化的接縫。
  • 待辦 點對點傳輸層 白皮書點名 Wi-Fi Aware／藍牙／NFC。先做一個就好，並保留 QR 作為零依賴的退路。
  • 技術驗證 Spike：離線的唯一性怎麼辦 nullifier 去重原本靠伺服器端資料庫。離線時無法全域去重——需要決定降級語意（單場域去重？時窗內去重？），這是設計決策，不是實作細節。
  • 待辦 撤銷清單離線快照 moica-revocation-smt 有提供離線二進位快照，需設計更新節奏與過期政策。
